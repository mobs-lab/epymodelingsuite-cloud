# CLAUDE.md

Serverless pipeline running epymodelingsuite workflows on Google Cloud (Batch + Workflows): Stage A builder → Stage B N parallel runners → Stage C output. See README and `docs/` for architecture, variables, and operations.

## Related Repositories

- **`epydemix`**: core epidemic modeling package (public PyPI), installed as a dependency of `epymodelingsuite` via its uv.lock.
- **`epymodelingsuite`** (`mobs-lab/epymodelingsuite`): config system, builders, dispatcher, calibration. Cloned into the Docker image at build time via `GITHUB_MODELING_SUITE_REPO` / `GITHUB_MODELING_SUITE_REF` (public, so `GITHUB_PAT` is optional for the build; it is still needed at runtime to clone the private forecast repo).

## Development

- **Always use `uv run`** for development (e.g. `uv run epycloud ...`, `uv run pytest`). The globally installed `epycloud` (`uv tool install`) does not pick up local code changes.
- All pipeline scripts serialize with `dill`, not `pickle`.

## Local Pipeline Runs

Set up `./local/forecast/` (mounted at `/data/forecast/`, added to `PYTHONPATH` by `run_builder.sh` in local mode):

```bash
cp -r <forecast-repo>/experiments/{EXP_ID} ./local/forecast/experiments/
cp -r <forecast-repo>/common-data ./local/forecast/ 2>/dev/null || true
cp -r <forecast-repo>/functions ./local/forecast/ 2>/dev/null || true
```

Then `epycloud run job --local --stage builder|runner|output ...` (outputs land in `./local/bucket/`). Gotchas:

- `RUN_ID` is generated by the builder stage and must be passed (`--run-id`) to runner and output stages.
- Output stage needs `--num-tasks` matching the runner count, and fails if any runner result is missing unless `ALLOW_PARTIAL_RESULTS=true`.
- `--output-config` picks among multiple output YAMLs; otherwise auto-detects (`output.yaml` first, then any YAML with an `outputs` key). Outputs go to timestamped `outputs/YYYYMMDD-HHMMSS/` dirs.
- `TASK_INDEX` (local) takes precedence over `BATCH_TASK_INDEX` (cloud).

## Docker Dependencies

The image installs `epymodelingsuite` with `uv sync --frozen` into `/opt/epymodelingsuite/.venv`, then installs cloud deps from `docker/pyproject.toml` + `docker/uv.lock` into that same venv with `uv export --frozen --no-dev | uv pip install -r -`. This is deliberate: `uv sync` would create its own `.venv`, while `uv pip install` respects `VIRTUAL_ENV`. To change cloud deps, edit `docker/pyproject.toml` and run `uv lock` inside `docker/`.

## Machine Types

Each stage uses an ordered fallback chain (`google_cloud.batch.stage_*.machine_types`): the workflow tries candidates in order (Stage B first moves candidates that pack the task count evenly to the front) and cancels/drains a candidate's Batch job before trying the next. Every candidate must meet the stage's `cpu_milli`/`memory_mib` minimums. A `--stage-*-machine-type` CLI flag pins one candidate and disables fallback. Stage C is memory bound: fallback chains must never step down in memory.
